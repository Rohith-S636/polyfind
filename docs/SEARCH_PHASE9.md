# Phase 9: Hybrid Search Architecture and Retrieval Pipeline

## 1. Overview and Data Flow

PolyFind implements a freshness-constrained hybrid retrieval pipeline combining authoritative relational keyword search (MySQL), derived dense semantic search (LanceDB), and graph relationship projections (Neo4j).

                      |   (polyfind:v1:listing:...) |
                      +--------------+--------------+
                             /               \
                       (hit)                   (miss / bypass)
                           /                       \
                          v                         v
               +----------------------+  +---------------------+
               | Strict Freshness     |  | Retrieval Planning  |

               +----------------------+  +----------+----------+

## 2. Retrieval Components

### A. MySQL Keyword Retrieval (`MySqlKeywordRetrievalProvider`)
- **Authoritative Source:** Queries the primary MySQL `products` table using parameterized SQL with `LIKE` pattern matching on `name` and `description`.
- **Structured Filters:** Directly pushes filters into the SQL `WHERE` clause:
  - `category_id = ?`
  - `price >= ?` (minPrice)
  - `price <= ?` (maxPrice)
  - `stock > 0` / `stock = 0` (inStock)
- **Scoring:** Calculates normalized token-overlap ratio ($\text{matchedTokens} / \text{totalTokens}$).
- **Version Tracking:** Emits `sourceVersion = products.version` for downstream verification.

### B. LanceDB Semantic Retrieval (`VectorSemanticRetrievalAdapter`)
- **Dense Vectors:** Queries the LanceDB `product_embeddings` table using cosine similarity on 384-dimensional dense embeddings generated by `TextEmbeddingProvider` (`DeterministicEmbeddingProvider` or OpenAI-compatible embedding service).
- **Tombstone Exclusion:** Filters out records where `deleted = true` directly within the LanceDB query (`deleted = false`).
- **Metadata Filters:** Applies category and price constraint predicates to LanceDB query vectors where supported.

## 3. Fusion and Ranking: Reciprocal Rank Fusion (RRF)

When multiple retrieval sources return candidate lists, they are merged using Reciprocal Rank Fusion (`src/fusion/rrf.ts`):

$$\text{RRF Score}(p) = \sum_{s \in \text{Sources}} \frac{1}{k + \text{rank}_s(p)}$$

- **Smoothing Parameter:** $k = 60$ (standard TREC optimal constant).
- **Properties:**
  - Scale-invariant: relies on ordinal rank rather than raw non-comparable scores.
  - Multi-source boosting: products discovered by both keyword and semantic paths receive higher cumulative RRF scores.
  - Deterministic tie-breaking: sorts by RRF score descending, breaking ties by `productId` ascending.

## 4. Freshness, Batch Hydration, and Filter Enforcement

MySQL remains authoritative for all transactional product attributes (price, stock, availability, title):
- **Bounded Batch Hydration:** Rather than N serial queries, candidates are hydrated in bounded batches (`catalog.getProducts(ids)`) preserving fusion rank order while eliminating latency amplification.
- **Post-Hydration Filter Verification:** After authoritative hydration, all structured filters (`minPrice`, `maxPrice`, `categoryId`, `inStock`) are strictly re-verified against the authoritative MySQL product facts (`matchesProductFilters`). Stale vector attributes cannot bypass filter bounds.
- **Deleted Product Exclusion:** If a candidate is absent from MySQL (`catalog.getProduct(id) === null`), it is treated as a deletion and immediately excluded (`safeToPresent: false`).
- **Version Verification:**
  - **Strict Mode:** If candidate `sourceVersion < product.version`, the candidate is flagged as stale and excluded.
  - **Best-Effort Mode:** Stale candidates are admitted only if safe, but their attributes are strictly hydrated from the current MySQL version.

## 5. Cache Strategy and Invalidation

- **Key Construction:** `buildSearchCacheKey` produces deterministic normalized keys encoding query, filters, retrieval strategy, and pagination:
  `polyfind:v1:listing:search:<mode>:q=<query>:<sorted-filters>:strat=<strategy>:p=<page>:l=<limit>`
- **Tracking & Reverse-Index Bounding:** Each cached search entry registers its contained product IDs under the reverse index `polyfind:v1:product-keys:<productId>`. Reverse index sets are assigned a bounded TTL (`2 * ttlSeconds`) to prevent unbounded Redis memory growth.
- **Invalidation:**
  - Product mutations (`updateProduct`, `deleteProduct`) invoke `invalidateProductStrict(productId)`, deleting all registered search cache entries containing that product.
  - Catalog-wide operations invoke `invalidateListingsStrict()`, deleting `polyfind:v1:listing:*` keys.
- **Graceful Bypass:** Any Redis error (timeout, connection drop) is caught silently, immediately falling back to direct retrieval without failing the user search.

## 6. Degraded Operation and Outage Behavior

| Condition | System Behavior |
| :--- | :--- |
| **MySQL Unavailable** | Throws `SafeDatabaseError` (sanitizing credentials/hosts), producing a controlled HTTP 503 response. |
| **Redis Unavailable** | Bypasses cache read and write; searches proceed directly against authoritative data. |
| **LanceDB Unavailable** | Catches error; drops `vector` from selected stores; seamlessly falls back to MySQL keyword search (`strategy: "adaptive-mysql"`). |
| **Embeddings Unavailable** | Vector retrieval fails gracefully; degrades to keyword-only search without user-visible error. |
| **Stale Semantic Data** | `FreshnessValidator` detects version divergence and discards stale candidates in strict mode. |
| **Product Deleted in MySQL** | Candidate resolution yields `null`; candidate is permanently dropped from results. |

## 7. Configuration for Semantic Search

To enable dense semantic search:
- `LANCEDB_PATH`: Path to the LanceDB data directory (default: `./data/lancedb`).
- `LANCEDB_TABLE`: Table name (default: `product_embeddings`).
- `EMBEDDING_PROVIDER`: Provider type (`openai-compatible`, as configured in `.env.example`).
- `EMBEDDING_ENDPOINT`: Embedding API endpoint (default: `https://api.openai.com/v1/embeddings`).
- `EMBEDDING_MODEL`: Embedding model name (e.g. `text-embedding-3-small`).
- `EMBEDDING_DIMENSIONS`: Vector dimension count (default: `384`).
- `EMBEDDING_TIMEOUT_MS`: Request timeout in milliseconds (default: `15000`).
- `EMBEDDING_API_KEY`: API key for embedding endpoint (also accepts `OPENAI_API_KEY`).
